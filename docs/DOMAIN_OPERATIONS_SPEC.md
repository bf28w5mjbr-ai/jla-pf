# 業務仕様整理（直近優先4テーマ）

この文書は、現行実装から読み取れる業務仕様を、直近で優先すべき4テーマに絞って整理したものです。
目的は「実装に着手できる粒度まで仕様を固定すること」であり、確定事項と未確定事項を明確に分けます。

## 1. 共通原則

- このプラットフォームは、ライフセービングに限らず `マリンスポーツ全体` を対象とする。
- ただし、直近導入先がライフセービング業界であるため、現行実装と一部業務ルールはライフセービング寄りになっている。
- 本仕様書では、プラットフォーム共通概念として `統括団体` を用い、現導入での具体例として `JLA` を併記する。
- `統括団体` と `大会開催者` は別役割として扱う。
- ただし、同一実体が `統括団体` と `大会開催者` の両方を兼ねることは許容する。
- 権限は `個人 / クラブ / 大会開催者 / 統括団体 / PF運営` で分離する。
- 重要な状態は `status` またはフラグで表現する。
- 重要操作は監査可能であることを前提にする。
- 統括団体は個人アカウントを直接運用しない。個人アカウント運用は `PF_ADMIN` の責務とする。
- クラブ運用はクラブ管理者、大会開催運用は開催者管理者に閉じる。
- 大会参加条件は「期間」「所属」「資格」「年齢」「性別」「大会状態」で機械判定できる形を優先する。
- 人件費削減と運用省力化のため、可能な限り `自動化優先` で仕様を組む。
- 競技ごとの差分ルールは、できる限り `競技ルールマスタ` に集約して管理する。

## 2. 優先順位

1. ユーザー登録とユーザー情報運用
理由: 全機能の入口であり、本人性・重複排除・連絡先整備が曖昧だと後続のクラブ/大会運用が崩れる。

2. クラブ作成と運用
理由: 所属承認、会費、代表者、クラブ管理権限が大会参加条件に直結する。

3. 大会開催者の作成と運用
理由: 大会作成権限の母体であり、主催責任と管理責任の所在を固定する必要がある。

4. 大会開催の運用
理由: 上記3テーマが固まると、大会の公開、募集、決済、結果公開の仕様を矛盾なく定義できる。

## 3. 新規登録とユーザー情報運用

### 3-1. 確定事項

- 登録フローは `基本情報入力 -> SMS OTP送信 -> OTP検証 -> User作成 -> ログイン状態付与 -> パスキー設定任意`。
- 登録時に保持する主要項目:
  - 氏名、氏名カナ、生年月日、性別
  - 電話番号
  - 住所
  - 緊急連絡先
  - メールアドレス
  - パスワード
- メールアドレスは新規登録時の必須項目とする。
- メールアドレスは本人通知だけでなく、統括団体・大会運営等からの正式な連絡先として利用可能であることを前提にする。
- 重複防止は少なくとも以下で行う:
  - 電話番号重複
  - メールアドレス重複
  - 正規化カナ氏名 + 生年月日
- SMS OTP は期限、再送クールダウン、時間あたり送信回数上限、試行回数上限を持つ。
- 登録完了時点で `phoneVerified = true` にする。
- SMS登録後でも `email/password` の追加設定を許可する。
- メールアドレス未確認でも、登録直後から通常利用を許可する。
- ただし、メール確認は通知・セキュリティ向上のため継続して促す。
- `電話番号・生年月日・氏名` などの重要属性変更は、本人による `パスワード再入力` を必須とする。
- `競技団体会員番号` の付与・更新主体は統括団体側とし、`PF_ADMIN` は通常運用では採番主体としない。
- 現導入では `競技団体会員番号 = JLA会員番号` として扱う。
- `PF_ADMIN` は、障害対応・移行対応・監査対応などの例外時のみ補助的に関与できる。
- 未成年ユーザーは、登録時に `保護者同意` を必須とする。
- 未成年ユーザーは、少なくとも `保護者氏名・続柄・連絡先` を必須で保持する。
- ユーザー本人による更新対象:
  - 基本プロフィール
  - 電話番号変更
  - セキュリティ設定
  - プロフィール画像
  - プライマリクラブ
- アカウント削除は本人操作を前提にする。
- アカウント削除は `物理削除` ではなく `論理削除` を基本とする。
- 論理削除後はログイン不可とし、監査・大会履歴・所属履歴の整合を壊さないことを優先する。
- 論理削除後も、公開済みの過去大会情報・結果表示などの履歴表示は維持してよい。
- 論理削除後は、本人・クラブ管理者・統括団体運用者が当該アカウントにアクセスまたは変更できない状態にする。
- ただし、当該ユーザーが `クラブ代表者 / クラブの最後の管理者 / 開催者の最後の管理者` であり、かつ当該組織が存続する場合は、後任設定が完了するまで削除不可とする。
- 統括団体はユーザー作成/削除/停止を行わず、個人アカウントの運用権限は `PF_ADMIN` のみとする。

### 3-2. 管理すべき状態

- 本人性:
  - `phoneVerified`
  - `emailVerified`
- 認証強度:
  - `passwordHash`
  - `mfaEnabled`
  - `passkeyCredentials`
- ライフサイクル:
  - `deletedAt`
  - `deletionScheduledAt`
- 論理削除後の見え方:
  - 公開済みの過去大会情報では履歴表示を維持
  - アカウント画面、プロフィール更新、所属操作、認証操作は不可
- 組織参加補助:
  - `primaryClubId`
  - `jlaMemberNumber`
  - `legacyJlaMemberNumber`
  - 将来的には `競技団体会員番号` として抽象化する

### 3-3. 未確定事項

- 現時点なし
### 3-4. 実装上の要確認

- 現在のアカウント削除は実質的に物理削除であり、仕様決定済みの `論理削除` へ実装変更が必要。
- `プロフィール更新` に厳密な入力検証と監査ログが十分に入っていない。
- 重要属性変更時の `パスワード再入力必須` を実装へ反映する必要がある。
- 実装上はメール未入力時に `@temp.jla.local` を補完する経路が残っているため、登録時メール必須の仕様に合わせて整理が必要。
- `jlaMemberNumber` などライフセービング前提の命名は、将来的にプラットフォーム共通概念へ抽象化する必要がある。
- 削除済みアカウントは通常運用からは不可視としつつ、`PF_ADMIN` が監査目的で閲覧できる導線を整備する必要がある。
- 未成年向けの `保護者同意` と `保護者情報` は現状スキーマ/入力フローに未反映のため、追加実装が必要。

## 4. クラブ作成と運用

### 4-1. 確定事項

- クラブ作成者はログイン済みユーザーとする。
- クラブは `作成時点で成立` する。統括団体承認待ちをクラブ成立条件にはしない。
- クラブ作成時、作成者の個人情報を初期代表者情報としてコピーする。
- クラブ作成と同時に、作成者の `Membership` を `APPROVED / ADMIN` で自動作成する。
- クラブの成立状態と `クラブ種別` の付与は分離して管理する。
- クラブ種別は作成直後は `未付与` を許容し、必要に応じて統括団体へ申請する。
- クラブ種別の `新規付与 / 変更` は、`統括団体` への申請対象とする。
- 現導入では `統括団体 = 日本ライフセービング協会（JLA）` として扱う。
- クラブ種別の `新規付与 / 変更` には、その都度支払いを伴う前提とする。
- クラブ種別付与/変更の支払いタイミングは `統括団体承認時` とする。
- クラブ種別の付与・変更は、`支払い完了後` に初めて有効化される。
- 初回申請では、支払い完了までは `種別未付与` を維持する。
- 種別変更申請では、支払い完了までは `現在の種別` を維持する。
- `クラブ種別未付与` であること自体は、クラブの成立や日常運用を妨げない。
- クラブ種別の利用制限は、必要に応じて `大会開催者が大会ごとの参加資格条件として設定する` 形を基本とする。
- `統括団体` はクラブの日常運用には介入せず、クラブ種別に関する `許認可` のみを担う。
- `統括団体` がクラブ情報にアクセスするのは、クラブ種別の審査・承認・付与に必要な範囲に限定する。
- 一般ユーザーはクラブに参加申請し、`PENDING -> APPROVED / REJECTED` の承認フローを通る。
- クラブ代表者は「当該クラブの承認済みメンバー」から選ぶ。
- クラブが存続する限り、常に少なくとも1名の `ADMIN` を維持する。
- クラブ代表者または最後の `ADMIN` が退会・削除・降格される場合、後任設定を先に完了していることを必須とする。
- ただし、クラブ自体を先に削除する場合は、最後の `ADMIN` 維持制約は適用しない。
- クラブの利用停止が必要な場合は、停止状態を `1種類のみ` 持つ。
- クラブの完全終了は、原則として `クラブ削除` で扱う。
- クラブ管理者は以下を運用できる前提とする:
  - クラブ基本情報更新
  - 代表者設定
  - メンバー承認/却下
  - メンバー役割変更
  - お知らせ
  - 活動記録
  - 会費年度設定、請求、領収書/請求書発行
- メンバー本人は退会可能とする。
- クラブ削除は管理者権限と確認入力を前提にする。
- クラブ削除は、少なくとも以下の条件を満たす場合のみ許可する。
  - 未処理のクラブ種別申請がない
  - 未払い請求がない
  - 進行中の大会エントリー管理主体になっていない
  - 実行者がクラブ名を再入力して確認している

### 4-2. 状態遷移

- クラブ:
  - `作成時点で成立`
  - 必要時のみ `停止` 状態へ遷移できる
  - 完全終了は `クラブ削除`
- メンバーシップ:
  - `PENDING -> APPROVED`
  - `PENDING -> REJECTED`
  - `APPROVED -> 退会または削除`
- クラブ種別申請:
  - `未付与または既存種別あり -> 申請(PENDING) -> 統括団体承認 -> 支払い完了 -> 種別確定`
  - `未付与または既存種別あり -> 申請(PENDING) -> REJECTED`

### 4-3. 未確定事項

- 現時点なし

### 4-4. 実装上の要確認

- クラブ運用の実質権限は `ADMIN` のはずだが、共通ガードが役割まで見ているかを要確認。
- クラブ作成時の文言では「オーナー」と案内しているが、データ上の役割は `ADMIN` のみ。
- 現行実装は `APPLYING / JLA_APPROVED / APPROVED` を前提にしており、「作成時点でクラブ成立」の新仕様と差分がある。
- 現行実装の年会費前提ロジックと、「種別付与/変更の都度課金」の新仕様との整合を取り直す必要がある。
- 現行スキーマには `SUSPENDED / INACTIVE` があるため、停止状態を1種類へ整理するならデータモデル見直しが必要。
- 現行のクラブ削除は確認名入力中心の実装であり、未処理申請・未払い・進行中運用の削除前チェックを追加する必要がある。
- 現行のアクセス制御は、`統括団体は許認可のみ` という新仕様に合わせて再整理が必要。
- 現行コードでは `JLA` という固有名詞が残っているため、プラットフォーム共通化する場合は名称整理が必要。

## 5. 大会開催者の作成と運用

### 5-1. 確定事項

- 大会開催者は `Organization` として管理する。
- `統括団体` と `大会開催者` は責務を分離する。
- `統括団体` は `許認可 / 会員番号付与 / ルール管理` を担う。
- `大会開催者` は `大会の作成と運営` を担う。
- 統括団体自身が大会を開催する場合は、`大会開催者` としても登録される。
- `統括団体` は、`大会開催者` の日常運用や大会運営に基本的に干渉しない。
- `統括団体` は、`大会開催者` の `作成 / 大会作成 / 公開 / 募集 / スタートリスト / 結果 / 返金判断` に関与しない。
- 開催者作成者はログイン済みユーザーとする。
- 開催者は `作成時点では仮状態` とし、料金支払い完了後に正式化する。
- 開催者作成時、作成者を初期代表者として扱い、同時に `OrgAdmin` を自動作成する。
- 各大会について「主催として表示する団体名・略称」は、大会作成時点の開催者プロフィールからスナップショットし、以後は当該大会上では変更しない（プロフィール上の団体名変更と連動しない）。誤記修正が必要な場合は別途運用で扱う。
- 開催者状態は少なくとも以下を持つ:
  - `PENDING`
  - `APPROVED`
  - `停止`
- 開催者にはオンボーディング費状態を持たせる。
- `PENDING` は仮状態、`APPROVED` は支払い完了後の正式状態として扱う。
- 開催者は常に少なくとも1名の `ADMIN` を維持する。
- 開催者の最後の `ADMIN` が削除・降格・除外される場合、後任設定を先に完了していることを必須とする。
- 開催者作成画面の先頭では、仮状態で作成されることと、正式化に必要な料金情報を事前に明示する。
- `PENDING` の開催者に許可する操作は、`基本情報編集 / 管理者設定 / 代表者設定 / 支払い実行` までとする。
- `PENDING` の開催者では、`大会作成 / 大会公開 / 本番運用系操作` は不可とする。
- 開催者の利用停止が必要な場合は、停止状態を `1種類のみ` 持つ。
- 開催者の管理メンバー追加は、`招待 -> 本人承諾 -> 参加確定` のフローを必須とする。
- `レコーダー` は独立主体ではなく、`大会開催者` 配下の限定権限として扱う。
- `レコーダー` 権限は `大会ごと` に付与し、開催者全体に一括付与するものではない。
- 開催者の停止理由は、少なくとも以下を想定する。
  - 規約違反
  - 料金未払い
  - 重大な運営事故対応
  - PF運営による一時停止判断
- 開催者管理者は以下を運用できる前提とする:
  - 基本情報更新
  - 管理メンバー追加
  - メンバー役割変更
  - メンバー削除
  - 代表者設定
  - ロゴ管理
  - 配下大会の作成
- 代表者は「当該開催者に所属する管理メンバー」から選ぶ。
- `レコーダー` 権限は、大会当日の記録入力・DSQ記録・順位補正など、競技記録に限定した操作のみ許可する。

### 5-2. 未確定事項

- 開催者名と略称の重複制御をどこまで厳格にするか。

### 5-3. 実装上の要確認

- 開催者運用の実質権限は `ADMIN` 想定だが、共通ガードと個別APIの整合を確認する必要がある。
- オンボーディング料金、正式化、停止の実行権限と解除フローを実装へ反映する必要がある。
- 現行実装では `PENDING` 開催者でも一部運用操作が可能な可能性があるため、開催者ステータスによる制御追加が必要。
- 現行スキーマの `SUSPENDED / INACTIVE` を、開催者側も `停止1種類` に整理するならデータモデル見直しが必要。
- 現行の開催者メンバー追加は即時追加方式のため、招待承諾フローへの実装変更が必要。
- 現行権限モデルでは、`統括団体は大会開催者に干渉しない` という原則を明確に制御できていない可能性がある。

## 6. 大会開催の運用

### 6-1. 確定事項

- 大会は `Organization` 配下で作成する。
- `APPROVED` の大会開催者のみが大会を作成できる。
- 大会開催者は、管理ページから `大会ページ` と `エントリーページ` を作成・公開する。
- 大会は `DRAFT` として作成し、正式化済み開催者であれば件数制限なく作成できる前提とする。
- 大会作成時の初期状態は `DRAFT`、公開時に `PUBLISHED`、その後 `ONGOING / COMPLETED / CANCELLED` を取り得る。
- 公開状態は `status` と `isPublished / publishedAt` を持つ。
- `DRAFT -> PUBLISHED` の公開条件は、少なくとも以下を満たすこととする。
  - 基本情報が入力済み
  - 開催日と会場が入力済み
  - エントリー期間が入力済み
  - 少なくとも1種目が存在する
  - 開催者が `APPROVED`
- `PUBLISHED` 後の変更は、`自由更新可の項目` と `制限付きの項目` を分けて扱う。
- `PUBLISHED` 後も自由更新可とする項目:
  - 大会説明
  - お知らせ
  - 添付資料
  - 後援・協賛・助成表示
  - 注意事項などの運用文面
- `PUBLISHED` 後は制限付きとする項目:
  - 参加費
  - 参加資格
  - エントリー期間
  - 種目
  - クラブ種別条件
- `PUBLISHED` 後の制限付き項目は、少なくとも以下のルールで変更を管理する。
  - `参加費`
    - 初回エントリー成立または支払発生前までは変更可
    - エントリー成立または支払が1件でも発生したら変更不可
  - `参加資格 / クラブ種別条件`
    - エントリー成立前は変更可
    - エントリー成立後の `厳格化` は不可
    - エントリー成立後の `緩和` は可。ただし告知必須
  - `エントリー期間`
    - 延長は可。ただし告知必須
    - 短縮は原則不可
    - 締切後の再開は主催者判断で可。ただし告知必須
  - `種目`
    - エントリー成立前は自由変更可
    - エントリー成立後の `削除` は不可
    - エントリー成立後の `追加` は可。ただし告知必須
    - エントリー成立後の既存種目の条件変更は原則不可
- 大会基本情報として少なくとも以下を持つ:
  - 大会名
  - 開催日
  - 会場
  - 説明
  - カテゴリ
- エントリー運用として少なくとも以下を持つ:
  - エントリー期間
  - 参加費
  - 参加資格
  - 参加対象者自由記述
  - 年齢条件
  - 所属クラブ必須フラグ
  - 複数種目エントリー可否
- 大会開催者は、参加資格条件として `許可するクラブ種別` を設定できる。
- クラブ種別条件は大会ごとのフィルタとして扱い、未設定の場合は制限なしとして扱う。
- したがって、クラブ種別条件を設定していない大会では、`種別未付与クラブ` も参加可能とする。
- 大会開催者が決定した運用情報は、原則として大会ページに掲載できるようにする。
- ただし、`運用文面` と `システム判定項目` は分離して管理する。
- `運用文面` は大会開催者が自由に編集できるものとし、少なくとも以下を含む。
  - 大会説明
  - お知らせ
  - 後援・協賛・助成
  - オフィシャル募集に関する案内
  - 注意事項
  - 添付資料
- `システム判定項目` は構造化して管理し、自由文で代替しない。
  - 開催日
  - 会場
  - エントリー期間
  - 参加費
  - 参加資格
  - クラブ種別条件
  - 種目
  - 公開状態
  - 結果
- 種目は大会配下で管理し、作成時に男女別レコードを対で持つ現行仕様を踏襲する。
- チーム種目は、種目ごとに `構成人数` を設定できるようにする。
- チーム種目の構成人数は、`ちょうどN人` で管理する。
- 一般参加者がエントリー可能なのは `PUBLISHED` の大会のみとする。
- 主催管理者は、`DRAFT` 状態でも内部確認用としてエントリー操作を行える。
- 個人エントリーは以下を満たした場合のみ受付する:
  - エントリー期間内、または主催管理者
  - 性別条件
  - 年齢条件
  - 必要資格
  - 所属クラブ条件
- 参加資格を満たさない場合は、その時点でエントリー不可とし、決済画面へ進ませない。
- `支払い完了` をもってエントリー成立とする。
- 支払い未完了の状態は、`エントリー手続き中` ではあっても正式な `エントリー成立` には含めない。
- チームエントリーはクラブ単位で管理し、クラブ管理者が更新する。
- チームメンバー割当は、`エントリー終了時 -> 該当レースの召集時刻まで` の期間で更新できる。
- `該当レースの召集時刻` は、大会開催者が当日に決定できる。
- チーム種目のスタートリスト表示は `チーム名のみ` とし、構成メンバーは掲載しない。
- 大会当日の現地運用は、`NFCタグ` を中心に行う前提とする。
- 選手は事前に、自身のアカウントと `NFCタグ` を紐付ける。
- `NFCタグ` は、`1アカウントにつき同時に1枚のみ有効` とする。
- `NFCタグ` の通常時の再紐付けは、本人が自分のアカウントに対して実行できるものとする。
- `NFCタグ` を忘れた場合や紛失した場合は、新しい `NFCタグ` をそのアカウントへ `上書き再紐付け` できるものとする。
- 大会当日の現地では、大会開催者も選手確認のうえで `NFCタグ` の再紐付けを代行できるものとする。
- チェックイン等の当日記録は `アカウント` に紐付くため、`NFCタグ` の差し替え自体は記録整合性を壊さない前提とする。
- `NFCタグ` の読み取りができない場合は、タグ記載の番号を入力する救済手段を用意する。
- タグ番号の `手入力救済` は、大会開催者側の端末からのみ実行できるものとする。
- その選手が出場するレースがある `各出場日の朝` に、`チェックイン` フローを設ける。
- 当日チェックインは、選手本人が `自分の携帯端末` に `NFCタグ` をかざして実行する。
- `チェックイン可能期間` は、大会開催者が `出場日ごと` に個別設定できるものとする。
- チェックインは `出場日ごと` に行う。
- チェックインは `本人のみ` 実行できるものとし、クラブ管理者による代理チェックインは不可とする。
- チェックイン済みの選手には、アプリ上で当日の `出場レース一覧` と `召集時刻` を表示する。
- 大会開催者が当日に `召集時刻` を変更した場合、チェックイン済み選手への通知を必須とする。
- 当日の `召集時刻` 変更通知のチャネルは、`アプリ内通知` のみでよいものとする。
- `チェックイン可能期間` 終了後でも、大会開催者は例外的に `手動チェックイン` を実行できるものとする。
- 例外的な `手動チェックイン` では、理由記録を必須とする。
- `チェックイン可能期間` 内に当日分のチェックインを行わなかった選手は、当日分を `欠場` として扱う。
- `召集` は、招集所の端末に `NFCタグ` をかざして手続きする。
- チェックイン済みであっても、`召集` に不在だった選手は `DNS` として処理する。
- チェックイン後に、体調不良その他の理由で本人から出場辞退の申告があった場合は、`棄権` として別状態で扱う。
- 本人による `棄権` 申告期限は、該当レースの `召集時刻まで` とする。
- `棄権` は、本人がアプリから申告できるものとする。
- 大会開催者も、聞き取り内容に基づいて管理画面から `棄権` を代行記録できるものとする。
- 大会開催者による `棄権` の代行記録は、`召集時刻後` でも可能とする。
- 競技中の失格は `DSQ` として別状態で扱う。
- `DSQ` は、大会開催者配下の限定権限である `レコーダー` が記録できるものとする。
- `大会開催者管理者` は、`DSQ` の確認および修正ができるものとする。
- `DSQ` を記録または修正した場合は、理由の記録を必須とする。
- したがって、`欠場` `DNS` `棄権` `DSQ` は別の運用状態として管理する。
- `欠場` は結果画面の表示対象には含めず、`スタート前離脱` として結果対象外にする。
- 結果表示では、`DNS` `棄権` `DSQ` をそれぞれの状態名でそのまま表示する。
- レース終了後は、選手が `NFCタグ` をレコーダー端末にかざすことで選手識別を行う。
- レコーダー端末では、`NFCタグ` をかざした順に順位を自動採番する運用を基本とする。
- 大会開催者配下の限定権限である `レコーダー` と `大会開催者管理者` は、必要に応じて後から順位を編集できるものとする。
- 順位を後から編集した場合は、修正理由の記録を必須とする。
- 順位の更新状況は、一般閲覧者にも `リアルタイム` で見えるようにする。
- リアルタイム表示される順位は `暫定結果` として扱い、`確定結果` と区別できるようにする。
- `暫定結果` の段階では、表彰対象順位は表示しない。
- `暫定結果 -> 確定結果` への切り替えは、大会開催者による明示操作で行う。
- `確定結果` になった時点で、表彰対象順位は自動表示する。
- 表彰対象人数を手動設定する機能は、初期仕様では持たない。
- 表彰対象人数は、`競技ルールマスタ` から自動決定する。
- `競技ルールマスタ` には、少なくとも `年齢区分 / 種目区分 / 必要資格 / 記録単位 / DNS・棄権・失格等の表記ルール / 表彰対象人数` を持たせる。
- `確定結果` の修正も許可する。
- `確定結果` を修正した場合は、`再確定` として扱い、修正理由の記録と履歴保持を必須とする。
- 大会エントリーの入金確定は `Stripe webhook` を正式な確定源とする。
- 管理画面での手動確認は補助的な確認行為に留め、正式な状態遷移の根拠にはしない。
- `エントリー受付状態` と `支払状態` は分離して管理する。
- `支払い待ち / 決済処理中` は内部手続き状態として管理し、`エントリー成立` とは明確に区別できることを必須とする。
- ただし、ユーザー向けUIでは `支払い操作は完了したが、入金確認中` という状態を明示できるようにする。
- したがって、ユーザー向けには `エントリー手続き完了` と表示してよいが、業務状態としての `エントリー成立` とは文言を分ける。
- 大会エントリー取消は以下のルールとする。
  - `エントリー締切前`: 支払い完了済みの本人エントリーは取消可能
  - `エントリー締切後`: 本人は取消不可、主催者のみ個別対応可能
- 返金は自動実行せず、主催者判断で個別に実行する。
- `エントリー締切後` の参加者情報修正は、権限ごとに以下のように扱う。
  - `本人`: 原則変更不可
  - `クラブ管理者`: 該当レースの召集時刻まではチームメンバー割当のみ可
  - `大会開催者`: 本人属性を除く、大会運用上必要な修正のみ可
  - `新規エントリー追加`: 原則不可、例外時のみ大会開催者が対応
- `告知必須` の変更は、少なくとも以下のチャネルで通知する。
  - アプリ内お知らせ
  - 大会詳細ページ上の更新告知
  - 該当参加者へのメール通知
- `SMS通知` は初期必須チャネルには含めないが、将来拡張として設計対象に含める。
- 大会お知らせは主催管理者が作成し、現行では即時公開する。
- 添付ファイルは主催管理者がアップロードする。
- スタートリスト（先頭ラウンド `HEAT`）は、エントリー締切（`entryEndDate`）後に初回スナップショット JSON が作成される。作成タイミングは定期 Cron に加え、主催がエントリー画面・種目スタートリスト画面を開いた際の補完呼び出しでも行う（いずれも「未作成かつ締切済み」のときのみ）。
- 管理画面の種目スタートリストでは、表示は原則エントリーの最新状態に追随する。スナップショットは締切時点の先頭ラウンド固定・進行記録・次ラ生成などに用いる。
- 種目ごとの「ステップ1（ラウンド別ヒート数）」確定後、先頭ラウンド各ヒートの次ラ進出枠（按分アップ）は次の式で試算する。総定員 `min(次ラウンドのヒート数 × 種目の最大レーン数, 当該種目の参加者総数)`。各ヒートへの配分は当該ヒート人数に比例し、整数化は最大剰余法とする（次ラ生成 API の按分モードと整合）。
- 一般公開ビューでは、スナップショット上で確定済みのラウンドのみを表示する。
- チームメンバー割当の変更は、ライブ表示には反映されるが、既にスナップショットで固定されたラウンドの並びは自動では書き換えない（主催の明示操作で記録更新可）。
- スタートリスト確定と結果確定の責任者は `大会開催者` のみとする。
- `統括団体` は、スタートリスト確定や結果確定の実務責任を持たない。
- 結果は `暫定 / 確定` を分けて保持し、一般閲覧では `暫定結果` のリアルタイム表示を許可する。

### 6-2. 推奨ライフサイクル

- `DRAFT`
  - 基本情報、種目、参加条件、料金、関係団体情報を編集中
- `PUBLISHED`
  - 一般公開開始、募集開始前後を含む
- `ONGOING`
  - 開催期間中
- `COMPLETED`
  - 開催終了、結果確定済み
- `CANCELLED`
  - 開催中止

#### 6-2-1. ステータス遷移契約（API固定ルール）

- 許可する遷移:
  - `DRAFT -> PUBLISHED` / `DRAFT -> CANCELLED`
  - `PUBLISHED -> ONGOING` / `PUBLISHED -> CANCELLED`
  - `ONGOING -> COMPLETED` / `ONGOING -> CANCELLED`
- 不可とする遷移:
  - `COMPLETED` または `CANCELLED` からの再遷移
  - `PUBLISHED -> DRAFT` など、上記許可遷移に含まれない全パターン
- 同一ステータスへの更新（例: `PUBLISHED -> PUBLISHED`）は no-op として許可する。

#### 6-2-2. `PUT /api/competitions/{id}/status` エラー契約

- `400 INVALID_STATUS`: 未定義のステータス値
- `400 INVALID_STATUS_TRANSITION`: 許可されない遷移
- `400 PUBLISH_REQUIREMENTS_NOT_MET`: `DRAFT -> PUBLISHED` 条件未達
- `403 FORBIDDEN`: 開催者管理権限なし
- `404 COMPETITION_NOT_FOUND`: 対象大会なし

### 6-3. 未確定事項

- `maxParticipants` は初期仕様では採用しない。必要性が明確になった時点で、`大会全体上限` を第一候補として後から追加検討する。

### 6-4. 実装上の要確認

- webhook を正式な入金確定源とし、`支払い完了 = エントリー成立` とする状態遷移を実装へ落とす必要がある。
- 現行実装では `CompetitionEntry.status` が単純なため、`決済手続き中 / エントリー成立 / 取消` などの表現方法を見直す必要がある。
- 大会のステータス遷移条件はAPIで自由変更できるため、業務ルールの固定が必要。
- `PUBLISHED` 後の制限付き項目について、変更条件と影響範囲を実装へ落とす必要がある。
- `告知必須` の変更について、アプリ内通知・ページ告知・メール通知の実装を整備する必要がある。
- `SMS通知` を将来拡張で追加できるよう、通知基盤の抽象化を意識する必要がある。
- `requiredQualifications` の候補は現状固定配列で、将来的には `競技ルールマスタ` と資格マスタに連動させる必要がある。
- 表彰対象人数を自動決定するための `競技ルールマスタ` が現行実装にない場合、その整備が必要である。
- 自由文編集領域とシステム判定項目をUI/APIで明確に分離する必要がある。
- お知らせは下書きなしの即時公開であり、公開承認や予約公開の仕様がない。
